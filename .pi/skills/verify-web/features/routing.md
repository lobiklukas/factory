# Routing

**Status: passing.** `/` redirects to `/sessions`, each section route renders inside the rail's
frame, and a session id that the control plane could not have minted is refused in the route rather
than sent to the API.

## Sub-features

- `/` redirects to `/sessions`: it is the only section with a real read behind it, and a redirect
  beats an empty first impression
- `/sessions` renders the list beside the pane; `/sessions/<id>` attaches to that session
- `/boards` lists the boards and `/boards/<id>` renders one board's lanes (LOB-75, [board.md](board.md));
  `/boards/not-a-board` is refused by `Schema.decodeUnknownOption(BoardInstanceId)` the same way.
  `?card=<task id>` opens the card pane and `?run=<session id>` one of its runs (LOB-76,
  [card-pane.md](card-pane.md)); a value that does not decode as that id is dropped, not sent
- `/sandboxes` renders an honest empty state naming the milestone (M4) that will back it, not a
  table with no source
- `/approvals` is every run's pending approvals (LOB-53): `listPendingApprovals`, polled every 2 s
  and re-read when a decision lands, newest ask first (so a run that just parked is on the page
  however many stale asks wait), counted from the server's `total` — a cut page says "Showing the
  newest N" — one block per asking session (a link to `/sessions/<id>`), each
  request an `li[data-approval=<request id>][data-approval-session=<session id>]` with
  `[data-decide=approved|denied]`. A click is `decideApproval` as `dashboard` with `resume: true`, so
  the parked run wakes with the answer; a decision recorded whose resume failed (`resumeFailed`) is a
  toast saying so, with a "Retry resume" action and the `factory approve … --id …` retry, never
  "not recorded"; with nothing pending it says `No approvals pending` and how a
  run comes to wait (`APPROVAL_REQUIRED`). Both routes are off the rail since LOB-76; `/approvals` is
  linked from a session pane that is waiting on one
- `/sessions/<id>` shows `[data-session-approvals=<id>]` above the transcript while the session has a
  pending approval, with the same Approve / Deny, and nothing visible when it has none — a hidden
  `[data-session-approvals-empty=<id>]` marks a loaded, empty list, so "no strip" can be told from
  "not loaded yet"
- `/sessions/not-a-real-id` is refused by the route's `Schema.decodeUnknownOption(SessionId)`, so the
  pane says what a session id is instead of surfacing a `not_found` the user cannot act on
- Every route renders inside the same frame: a 48px icon rail, then the route

## How to get to it (user POV)

Open the dashboard root. No auth, no query parameters, no seed data.

## Driving it with drive.mjs

`drive.mjs` asserts the redirect, the copy on `/sandboxes`, the approvals inbox, and the bad-id
refusal. Below `md` a session's route hides the list whatever its id decodes to (LOB-210), so the
refused pane carries the same **Show sessions** link as a session's header: the drive requires it
hidden at 1440 px, visible at 390 px, and opening `/sessions` (`observed.badIdBack`). The sandbox assertion is deliberately on the copy: a table appearing without a source behind
it fails the run.

The approvals block (LOB-53) flipped the old "approvals says what is missing" check rather than
deleting it. On a fresh session the drive calls `requestApproval` itself (what a gated call does),
then asserts:

1. **the session pane shows its pending approval** — `[data-session-approvals]` holds the request;
2. **approvals shows the pending approval and decides it** — `/approvals` lists it under its session
   (the M3 copy is gone), `listPendingApprovals` from the drive holds it, one click on Approve sends
   exactly one `decideApproval` (`approved`, actor `dashboard`, `resume: true`), the row detaches, and
   the API's list no longer holds it;
3. **the decided approval resumed its session** — `getSession` from the drive holds the follow-up
   ``Approved: `verify-web: publish the package` … approved by dashboard.`` and an answer to it;
4. **the session pane drops the decided approval** — on reload the pane's loaded-and-empty marker
   `[data-session-approvals-empty]` appears, and only then is `[data-session-approvals]` counted (0),
   so a read that is slow or failed cannot pass for an empty one.

## Gotchas

- The empty-state copy is asserted by the driver, so it is load-bearing. `No sandboxes yet` + `M4`,
  `Not a session id this control plane mints` and `Not a board id this control plane mints` must
  survive an edit. `No approvals pending` is not asserted: other runs on the same database may leave
  requests pending, so the drive asserts its own request instead of an empty inbox.
- `src/routeTree.gen.ts` is generated by the Vite plugin and committed, because `tsc` reads it. Adding
  a route file regenerates it; deleting the route file restores it, so a scratch route leaves no diff.
- `/sandboxes` is a named gap, not a feature. See the feature map's gap list.
- The approval is seeded through `requestApproval`, not by a gated call: `up.sh` starts the API
  ungated. The gated path — a run that parks and resumes — is driven from the terminal by
  `.pi/skills/verify-cli/approve.sh`; both call the same `decideApproval`.
